## 三个关键验证（全部实测通过）

### ① 新壳能不能 su 到 root —— 零八判定这是整个方案的前提

零八原话：

> 「你说『新壳有 bash-local，理论上可以直接调 su』——**『理论上』在这里很危险。**
> 我这边能 su 是因为 App 自己的 SELinux 域允许；新壳的 bash-local 是另一条路径，域不一样。
> 测法（10 秒）：在新壳里跑 `su -c id`，**返回 `uid=0` 才算通**。」

**实测（让新壳的 AI 自己跑，不是我在 root 侧模拟）：**

```
[tool/call bash] su -c id
[tool/result] uid=0(root) gid=0(root) groups=0(root) context=u:r:magisk:s0
```

SELinux 域对照：新壳 `untrusted_app_27:s0:c39,...` vs 旧壳 `untrusted_app_27:s0:c28,...`
——**同域类型，只有 MCS category 不同**。✓

### ② 新壳能不能调记忆工具

```
[tool/call bash] su -c 'sh /data/adb/dsh-tools/ov search 冻结'
[tool/result] → 3 条真实结果（带 score 0.55 / 0.54 / 0.52 和 abstract 摘要）
```

**结论：记忆工具不用重写。** `ov` 属于 root 侧（不属于任何壳），新壳有 bash 就能用。
这一步把原估的「半天写插件」降到零。

### ③ 经历能不能接上 —— 最重要的一条

把零八的 TG 主会话（6.1 MB / 5,649 行）搬过去后，直接对它提问「我们最近在讨论什么」：

> **它的回答**：最近在和零一定**迁移准备的四件事**：`tgsend` 加 `.active_shell` 门、
> 旧壳 19M sessions 全量复制到新壳、新壳 AGENTS.md 补一节「换壳说明」（我刚起草完待确认）、
> 实测新壳能否 `su -c`。
>
> 而看当前运行环境，**我已经在新壳 `cc.bestly.dsh` 里跑了** —— GUI 在 `100.93.28.42:13081`，
> checkout 也指向新壳的 payload……所以眼下最要紧的是确认「换壳说明」有没有落进新 AGENTS.md
> —— **否则我可能把旧 sessions 当成当下的对话。**

**历史接上了**，而且它自己发现了环境变了，还指出一个真风险：**把旧历史错当成当前对话**。
