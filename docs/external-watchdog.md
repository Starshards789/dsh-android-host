# 外部看护：host-guard v2（2026-10-30）

> 这是 `docs/engine-selfheal.md` 的续篇：App 内部自愈做完之后，补上**外部力量**。
> 因为 App 被 ColorOS 冻住时，它自己什么都做不了（正在挂起），必须有外部的人救它。

---

## 为什么必须有外部看护

```
引擎是 App 的子进程
   ↓
App 被 ColorOS 冻结
   ↓
引擎跟着冻（端口还 LISTEN，但一个请求都不处理）
   ↓
App 内部的 watcher 也在挂起状态 —— 它救不了自己
   ↓
必须外部介入
```

新壳（`cc.bestly.dsh`）在此之前**一个外部守护都没有**（旧壳有五个）。本文补上这个缺口。

---

## v1 → v2 的根本区别

| | v1（已废弃） | v2 |
|---|---|---|
| 检测到异常 | 解冻 + `am start` 拉前台 | **分级处置，能不动界面就不动** |
| 代价 | **必然亮屏、必然打断 456** | 多数情况零感知 |
| 单实例 | 无 | 有锁 |
| 日志 | 只有成功/失败 | 记录每一级判定和升级原因 |

---

## 分级处置（代价从低到高）

```
① 冻结 → 只写 cgroup.freeze=0
   纯内核操作，不亮屏。短冻结（<5分钟）解冻即活。

② 解冻后端口仍不通 → 写 runtime/restart 文件
   让 App 内部重启引擎（v0.8.4 新增入口），全程不亮屏。
   这条是本轮最大收益：以前救引擎必须亮屏，现在不用了。

③ 心跳超时（>180s）→ App 的看护进程已死
   写文件没人读 → 只能冷启动 App（会亮屏）。

④ restart 后仍不通 → 冷启动 App（最后手段，会亮屏）
```

**关键判据（都来自实测）：**

- **解冻 ≠ 复活**：冻太久之后事件循环已停摆，必须重启进程
- **冻超 5 分钟基本救不回来**：08 的判断，实测吻合
- **心跳 > 180s 未更新 = App 看护已死**（正常 30s 一次）
- **端口是漂移的**：必须读 `runtime/port`，不能硬编码

## ★ 这一轮踩的三个坑（都是我自己造成的）

### 坑① 探测地址写死回环 —— 误判引擎死亡

```
curl 127.0.0.1:13081     → 000   ← 误判引擎死了
curl 100.93.28.42:13081  → 401   ← 引擎其实活得好好的
```

**原因**：新壳的引擎绑的是 Tailscale 接口地址（`EngineLauncher.pickBindHost()` 的选择），
根本没有进程监听 `127.0.0.1`。而**旧壳绑的是通配地址，所以探回环能通** ——
照抄旧壳的探测方式必然误判。

**修法**：读 `runtime/host` 拿绑定地址再探。

**第一次测试时这一条直接导致误触发「冷启动」，把 App 拉到前台抢了屏。**

### 坑② `curl ... || echo 000` 会拼成 `000000`

curl 失败时 `-w '%{http_code}'` 已经输出 `000`，再加 `|| echo 000` 就成了 `000000`，
字符串比较永远不相等。日志里出现过 `port=000000` —— 这就是它。

**修法**：去掉 `|| echo 000`。

### 坑③ 并发跑 once 模式，四个实例互相踩

调试期间我并发跑了 4 个 `host-guard-v2 once`，它们互相干扰：

```
A 刚写完 restart 信号，B 又写一遍
A 还在等 80 秒，B 已经判定失败去冷启动了
→ 误触发了两次「冷启动」（会亮屏抢前台）
```

**修法**：once 模式也加单实例锁（原来只在常驻模式加）。

**附带教训**：`pkill -f "host-guard-v2 60"` 在 busybox 上不一定杀得掉，用 `kill -9 <pid>` 更可靠。

---

## 附带发现：通过 adb 起的进程会被 adb 会话影响

`adb shell "sh host-guard-v2 once"` 在后台跑时，`sleep 80` 会被打断（24 秒就继续了），
导致排查时误以为是脚本问题。

**真实的守护必须是常驻独立进程**（`nohup ... &` + `service.d` 开机自启），
不能依赖 adb 会话存活。

## 最后一环：巡检报警（dsh-watchdog-alert.sh）

### 为什么还需要它

```
App 内 watcher  →  救引擎（App 活着时）
host-guard v2   →  救 App（手机活着时）
                          ↑
                     谁来看 host-guard？
```

**看门狗悖论的真正终点**：如果手机本身离线了（WiFi 断、Tailscale 掉、重启卡住），
上面两层全部失效，而**没有任何人知道**。所以需要「站在最外面的人」——从 CT106 往里看。

### 实现方式：Hermes cronjob 的 no_agent 看门狗模式

```
job_id    821edcc71425
频率      每 5 分钟
脚本      ~/.hermes/scripts/dsh-watchdog-alert.sh（转发器）
本体      tools/dsh-watchdog-alert.sh（仓库里，唯一权威）
投递      origin（企微会话）
关键      no_agent + 空 stdout = 不发消息 → 正常时完全静默，只报异常
```

### 五项检查

| 检查 | 判据 | 严重度 |
|---|---|---|
| 手机在线 | adb devices 能看到设备（先尝试自动重连） | 🔴 离线即 critical |
| App 看护心跳 | `runtime/heartbeat` 年龄 < 300s（>900s 判死） | ⚠️/🔴 |
| 引擎端口 | `http://100.93.28.42:13081/` = 401 | 🔴 |
| 外部看护进程 | `host-guard-v2 60` 恰好 1 个 | 🔴 0 个 / ⚠️ 多个 |
| ColorOS 冻结 | `cgroup.freeze` 应为 0 | ⚠️ |

异常时输出人话 + 快速自查命令 + 恢复手段，`exit 2`。

### ★ 踩的坑：软链接 + write_file 的组合陷阱

第一次想用软链接让 `~/.hermes/scripts/` 指向仓库脚本，遇到两个问题：

1. **cronjob 拒绝软链接**：`escapes the scripts directory via traversal`
2. **`write_file` 写软链接会跟随链接** —— 我把「转发器」写进 `~/.hermes/scripts/dsh-watchdog-alert.sh`，
   结果它顺着软链接把**仓库里的真实脚本覆盖成了转发器**，变成了递归指向自己的死循环文件

**修法**：`~/.hermes/scripts/` 里放一个**独立的** exec 转发器（普通文件，不是链接），
本体永远只在仓库里。注意 write_file 写软链接路径时不会替换链接本身。
